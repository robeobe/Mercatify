# Prove a cross-cutting invariant on the composed artifact, not on the component that states it

**Context**: Two blockers in `mercatify-labs` shared one shape. (1) `src/toolVerdict.ts` was fixed so an off-catalog capability never banks a saving, and its unit test was green; the report still charged that capability, because the cost side runs through `src/report/waves.ts`, which had never heard of the concept — `Wave.scope` took the item, `Wave.hours` took its 16 hours, and the document grew a wave titled `TBD — needs discovery` that moved `implementationCost` 19,800 → 21,720, `programmeWeeks` 23 → 26, `breakEvenMonth` 15 → 16 and `netAtHorizon` 40,435 → 37,751. (2) Section 02 printed `38 usage statements` from the consultant's counters while Figure 1, two pages later, printed `15 usage statements` from `coverage.byVerdict` — same unit word, two different sets, in every report the engine produced. Both components were individually correct, and both comment blocks asserted the opposite ("ten sam licznik stoi w sekcji 02"). The golden master was green on a hand-written `voltix.reportmodel.json` whose `byVerdict` sums to 38 — an input the pipeline cannot produce, so the one test positioned to catch it was measuring a model out of the engine's reach.

**Problem**: An invariant like "this never enters a figure" or "these two numbers agree" is not a property of any one function; it is a property of the artifact several functions compose. Every component can satisfy its own contract while the composition violates the rule, so unit-level green is not evidence and a second unit test on the next component only moves the seam. A golden-master or fixture test looks like the missing coverage but silently stops being one the moment its fixture drifts to a state the pipeline cannot reach — and nothing about it turns red to say so. The comments are the tell: when two files each describe the same quantity and one of them is wrong, the disagreement has usually been shipping for a while.

**Rule**: When a fix enforces a rule that spans components — an exclusion from every figure, two counters that must agree, a value that must not reach an output — write the regression test on the **end-to-end** artifact (here `buildReport` → `renderReport`, asserting on the finished HTML and on whole fact objects such as `facts.waves` / `facts.cash`, not on hand-picked fields, so a new hour- or money-carrying field fails on its own). Then verify the test by reverting the fix and watching it go red; a test that stays green over a reverted fix is documentation, not coverage. Prefer a differential assertion — two full runs that must be identical except in the places that should differ — over asserting recomputed constants. Before trusting an existing fixture test, check that the engine can actually produce that fixture. And when two numbers legitimately describe different things, do not force them equal and do not invent the decomposition: give each its own unit word and make the document state the difference in a sentence.

**Applies to**: `mercatify-labs/src/report/waves.ts`, `src/report/counts.ts`, `src/report/templates/coverage.ts`, `src/report/templates/basis.ts` and `src/toolVerdict.ts`; the composed-run tests in `src/__tests__/buildReport.test.ts` (blocks `B4`, `B5`) and the fixture-bound golden master in `src/__tests__/renderReport.test.ts`; the report pipeline specified in `.ai/specs/2026-09-19-mercatify-report-pipeline.md`.
